## 一、项目意义评估

### 1.1 需求真实存在，且痛点明确

**结论：需求成立，但项目当前的实现方式与其宣称的价值主张存在根本性冲突。**

真实的落地场景是清晰的：

- **医学 / 公共卫生定性研究**：访谈逐字稿含可识别信息，医院伦理委员会（IRB）通常禁止将原始访谈文本上传至任何第三方云服务——包括国内云厂商。这不是"偏好"，而是审查红线。
- **中国高校科研合规**：涉及《个人信息保护法》（PIPL）与医学伦理审查。数据"不出境"只是最低要求，多数校内伦理批件要求的是"不出内网/不出校"。
- **欧盟 GDPR 场景**：PRD 明确以 GDPR 为卖点。但把访谈数据发往境外云服务，恰恰是 GDPR 场景下最敏感的跨境传输行为。

这个需求之所以真实，是因为**商业软件在这一点上是结构性缺失的**：

| 工具 | 本地/离线能力 | AI 编码能力 | 二者能否同时满足 |
| :--- | :--- | :--- | :--- |
| ATLAS.ti Desktop | 完全离线可用 | AI Coding **由 OpenAI 驱动，需联网** | ❌ |
| NVivo | 桌面本地 | AI Assistant 为独立付费插件，云端 | ❌ |
| Taguette | 自托管 Docker | **无 AI** | ❌ |
| QualCoder | 桌面本地 | **无自动编码** | ❌ |
| RQDA | 本地 | **无 AI**，且已停止活跃开发 | ❌ |
| **QualiCraft（目标形态）** | 本地 | 本地 LLM | ✅ |

**"本地部署 + AI 辅助编码 + 人工复核"这个交集，在现有市场上确实是空白。** 这是本项目最有价值的战略判断，值得坚持。

### 1.2 与 ATLAS.ti 的差异化分析

**QualiCraft 的真实优势：**

1. **AI 编码过程可审计**——这是目前最被低估的优势。系统强制要求模型返回"原文精确子串 + 字符偏移量"，服务端做严格校验：引文无法在原文中唯一匹配的建议**直接丢弃**，不进入候选池；所有建议必须由研究者逐条 Accept 才能转为正式编码。ATLAS.ti 的 AI 是黑盒式"生成一组编码"，而 QualiCraft 把每一条 AI 判断都钉在了原文坐标上。对需要写方法学章节、需要向伦理委员会解释"AI 在研究中扮演什么角色"的研究者，这个设计价值很高。
2. **内置自动化一致性评测**——`evaluate.py` 用最大基数二分图匹配做一对一引文/编码匹配，输出精确率、召回率、F1、IoU。**ATLAS.ti 和所有免费开源工具都没有这个能力。** 对想做"AI 编码 vs 人工编码一致性"方法学研究的团队，这是真正的差异化。
3. **源码可审计**——伦理审查时可以直接向委员会展示代码，证明数据流向。商业闭源软件做不到。
4. **零依赖部署**——纯 Python 标准库，无需 `pip install`，无需 Docker。在一台普通笔记本上 30 秒跑起来。对"不想在实验室服务器上装一堆东西"的团队是实际优势。
5. **免费 + MIT 协议**——ATLAS.ti 学生版约 $51–99/年，校园站点授权约 $2,400/年起；NVivo 的 AI 插件另需约 €230/年。

**QualiCraft 的明显不足（相对 ATLAS.ti）：**

| 维度 | ATLAS.ti | QualiCraft 当前 |
| :--- | :--- | :--- |
| 多媒体编码 | 文本/图片/音频/视频 | **仅文本** |
| 音频转录 | 集成第三方转写 | **无** |
| 码表层级 | 完整层级树、拖拽、合并 | **扁平列表，无层级** |
| 编码者间信度（IRR） | 完整支持（Kappa 等） | **无**（评测只对比模型 vs 参考标注，非双人编码） |
| 协作 | 云端实时多人共同编码 | **无**（无账号、无用户体系） |
| REFI-QDA 互通 | 完整导入导出 | **无** |
| 可视化 | 网络图、共现分析、词云 | **仅频次条形图 + 文档×编码矩阵** |
| 成熟度 | 30+ 年，教学资源丰富 | MVP，单日冲刺产物 |
| 生态/文献引用 | 学术界事实标准 | 无 |

### 1.3 最关键的发现：核心价值主张尚未兑现

PRD 第 1 节把 **"100% 本地合规（GDPR Ready）——彻底杜绝云端商业 API"** 列为**第一差异化壁垒**。但实际代码的默认行为是：

```
默认端点：https://dashscope.aliyuncs.com/compatible-mode/v1   （阿里云百炼 · 北京）
默认模型：qwen3.8-flash
```

也就是说，**当前版本把访谈文本发送到公有云**。团队在 `docs/ARCHITECTURE.md` 中明确写道该文档"取代了早期假设完全本地化语言模型的规划笔记"——这是一个主动的、被记录在案的架构降级。

同时必须指出：**这个降级在当前形态下是不可接受的**，因为：

- 对医院 IRB 场景，发往任何公有云（包括国内）都可能直接违反伦理批件；
- 对 PRD 主打的 GDPR 场景，发往境外云反而制造了跨境传输合规风险；
- 这样一来，QualiCraft 相对 ATLAS.ti 桌面版的**唯一硬差异（本地 AI）消失了**——ATLAS.ti 桌面版本身就能离线工作，用户没有理由迁移。

**但是，架构上留了后门，这是好消息。** `validate_config()` 允许 `http://127.0.0.1` / `localhost` 端点：

```python
require(parsed.scheme == "https" or (parsed.scheme == "http" and
        parsed.hostname in {"127.0.0.1", "localhost", "::1"}), ...)
```

这意味着接入本地 vLLM / Ollama / LM Studio **不需要改一行代码**，只需在设置里改端点。缺的不是能力，而是**一份本地推理的部署方案和文档**（无 Dockerfile、无 vLLM 配置、无 `docker-compose.yml`）。

### 1.4 需要提醒的产品决策

UI 目前**全英文**（提交 `a7558c8` "Build English local qualitative coding workspace" 是刻意决策）。如果目标用户是中国高校研究者与医院临床团队，这会在推广时形成实际阻力——PRD 本身是中文撰写的。解析层倒是支持中文说话人标签（`患者/医生/受访者` 等），但界面无 i18n 框架。

**建议：** 若目标市场是国内高校，至少应规划中英双语；若目标是国际期刊合作项目，保持英文合理，但需明确写进定位文档。

| 评估项 | 判断 |
| :--- | :--- |
| 需求真实性 | **高**——医学伦理审查与数据主权是硬约束 |

- 访问日志主动关闭（`log_message` 空实现），避免逐字稿内容落盘

**另一个值得肯定的点：团队有罕见的学术诚实。** `docs/GUIDE_DATA_AUDIT.md` 主动纠正了自己 PRD 中的 7 处夸大表述，例如：

## 三、改进建议

### 3.1 P0 —— 决定项目生死的问题

#### （1）落地本地推理，兑现"本地部署"承诺

**这是第一优先级，其他所有改进都排在它后面。** 现状是：项目叫"本地部署平台"，但 AI 能力依赖公有云；而 AI 恰恰是它唯一的差异化。

具体动作：

- 新增 `deploy/` 目录，提供 **Ollama** 与 **vLLM** 两套本地推理方案：
  - `ollama` 路线（推荐先做）：`ollama pull qwen3:14b` → 端点填 `http://127.0.0.1:11434/v1`。零改代码即可跑通，适合单机研究者。
  - `vLLM` 路线：面向实验室 GPU 服务器，提供启动脚本与显存估算（如 32B 模型需多少张卡、Tensor Parallel 配置）。
- 提供 `docker-compose.yml`，一条命令拉起"应用 + 本地推理"。
- 在设置界面增加"本地模型 / 云端模型"的显式切换，并把默认值改为**本地优先**。
- 文档中明确写出各方案的硬件门槛，让用户能自行判断可行性。

**验收标准：** 在一台断网的机器上，完成"导入访谈 → 本地模型建议 → 人工采纳 → 导出"全流程。

#### （2）让"可部署在高校"成为事实，而非愿景

当前架构**无法**直接部署到实验室局域网或校园内网，原因是硬编码：

```python
# server.py:172  —— 只监听回环地址
server = ThreadingHTTPServer(("127.0.0.1", port), Handler)

# server.py:51   —— Host 白名单写死
allowed = {f"127.0.0.1:{self.server.server_port}", f"localhost:{self.server.server_port}"}
```

同时存在一个**在多用户场景下致命的认证缺陷**：

```python
# server.py:62  —— /api/bootstrap 无需任何凭证即可返回会话令牌
if path == "/api/bootstrap":
    return self.send({"token": token, "projects": store.list(), ...})
```

**任何能访问该端口的客户端，只要打开页面就能拿到 token，从而读写全部研究项目。** 这在单机 `127.0.0.1` 下是合理设计（威胁模型已声明），但一旦为了"实验室共用"而放开监听地址，就等于**所有项目对全网段开放**。

具体动作：

- 增加 `--host` 参数与 `--allowed-hosts` 配置，替换硬编码。
- 引入最小用户体系：本地账号 + 密码（或对接学校统一身份认证 CAS/OIDC），项目按 owner 隔离。
- `/api/bootstrap` 必须认证后才下发 token；token 与用户会话绑定，而非进程级全局共享。
- 增加 CSRF token 与登录态过期。
- 明确区分两种部署模式并写入文档：**单机模式**（保持现状）与 **共享模式**（需要账号体系）。

#### （3）补齐码表与文档的基础管理能力

当前**无法重命名、删除、合并编码，也无法删除文档**。服务端只有 `add_code` / `add_document`，没有任何 update/delete 对应实现（实测确认）。这在真实研究中是硬伤——编码方案必然会在分析过程中迭代重构。

具体动作：编码改名 / 改定义 / 改色 / 删除（级联处理引用）/ 合并；文档删除；编码层级（parent_id + 拖拽 + 折叠）；操作撤销。

### 3.2 P1 —— 决定项目是否"够用"的问题

#### （4）模块 C 绘图工作台：要么认真做，要么从宣传中移除

这是 PRD 的"核心杀手锏"，也是当前 0% 的部分。建议分两步：

- **第一步（1–2 周，低风险）**：先做纯前端渲染，不引入 R/Docker。
  - 用 Chart.js（已在可用 CDN 白名单内）实现**主题共现热力图**与**发散条形图**，数据源就是已有的"文档 × 编码"矩阵。
  - 这一步能立刻交付"可发表的图"，且不增加部署复杂度。
- **第二步（3–4 周）**：再评估是否值得引入 R 沙箱导出 TIFF/SVG。建议优先用 Python（matplotlib/seaborn）而非 R，减少一层技术栈。
  - 若坚持要 R，`ComplexHeatmap` 的双向聚类效果确实更好，但需要 Docker 隔离，部署门槛会显著上升——这与"轻量本地部署"的定位存在张力，需要权衡。

**如果这一步不做，建议同步修改 PRD 与 README**，把绘图从"核心杀手锏"降级为"规划中"，避免向导师或评审做出无法兑现的承诺。

#### （5）补 REFI-QDA 导出，这是低成本高回报

REFI-QDA 是 QDA 领域唯一的跨软件交换标准。加上它，QualiCraft 就能：

- 让研究者把结果**导回 NVivo / ATLAS.ti / MAXQDA** 继续精修，大幅降低试用心理门槛；
- 让 QualiCraft 成为"AI 预处理 + 商业软件精修"流程中的一环，而不是要求用户全盘迁移。

导出比导入容易得多（只需按 XSD 生成 XML 包）。**建议优先做导出，导入次之。**

#### （6）补齐编码者间信度（IRR）

IRR 是定性研究方法学的标准要求，也是审稿人常问的问题。当前 `evaluate.py` 只能对比"模型 vs 参考标注"，**不支持两位人类编码者的一致性计算**。

好消息是：**算法基础已经存在。** `evaluate.py` 里的 `iou()` 与最大基数二分图匹配可以直接复用到 Cohen's Kappa / Krippendorff's Alpha 的实现上。建议：

- 引入"编码者"概念（即使只是本地命名）；
- 支持同一项目内的多套编码记录；
- 计算并展示 Kappa / Alpha。

#### （7）性能架构：从"整包 JSON"改为关系表

实测数据（20 文档 × 50 万字符 = 1000 万字符，20 编码）：

| 指标 | 实测值 |
| :--- | :--- |
| 项目 JSON 体积 | **9.6 MB** |
| 单次打标写入耗时 | **52 ms**（每次重写整个项目） |
| 单次 GET 全项目响应 | **9.6 MB** |

按代码中声明的上限（100 文档 / 项目）外推，**单个项目 JSON 约 48 MB，而它会在每一次点击时被完整重写并完整下载。**

根因是 `Store` 把整个项目（含全部逐字稿）序列化成一个 JSON 存在单行 SQLite 里，`Store.change()` 每次操作都读出、反序列化、整体写回。前端 `refresh()` 也在每次操作后重新拉取全量项目并整体重建 DOM。

具体动作：

- 拆表：`documents` / `codes` / `annotations` / `suggestions` / `audit` 各建独立表，只写变更行。
- 文档正文单独存储，列表接口不返回 `text`。
- 前端改为增量更新，避免全量 `refresh()` 与全量 `innerHTML` 重建。
- **落实 PRD 早已提出的"虚拟文本切片"**：当前 `readerHtml()` 会把长文档的全部段落一次性渲染进 DOM，50 万字符的逐字稿会产生数千个 DOM 节点。

#### （8）任务状态需要持久化

`self.jobs` 与 `self.previews` 都只在内存中（`ai.py:123`）。服务重启后：进行中的分析丢失、预览失效、无断点续跑。另外全局**同时只允许一个分析任务**，多文档并行处理无法实现。

建议：任务表落库；支持断点续跑（逐段提交的结果其实已经落库了，只需记录进度指针）；放开并发限制。

## 四、总体结论

**这是一份质量显著高于同类的 MVP，但当前处于"名实不符"的危险位置。**

**做对了的事：**

- 选了一个真实且尚未被满足的赛道——"本地部署 + AI 辅助编码 + 人工复核 + 可审计溯源"，这个交集在 ATLAS.ti、NVivo 以及 Taguette/QualCoder 等开源工具中确实都不存在。
- 核心交互（偏移量锚定、Margin 胶囊标签、AI 建议审核卡片、引文精确校验）已经跑通，且实机观感接近 ATLAS.ti 的现代风格，不是纸面设计。
- 工程纪律扎实：零依赖、16 项回归测试、CI、严格 CSP、事务回滚、CSV 注入防护、密钥隔离。这些都是能写进简历的实打实功底。
- 学术诚实度高，主动纠正了自己 PRD 中的夸大表述——这一点比多写几千行代码更珍贵。

**最需要正视的事：**

1. **"本地部署"这个立身之本没有兑现。** 默认把访谈文本发往阿里云，与医院伦理审查、GDPR 场景直接冲突，也使项目相对 ATLAS.ti 桌面版的差异化归零。这是必须在下一个迭代解决的第一问题。好在架构允许本地端点，改造成本不高，缺的是部署方案而非代码能力。
2. **被定义为"核心杀手锏"的绘图工作台完成度为 0。** 叙事与代码之间存在巨大落差，需要要么补上，要么修正宣传口径。
3. **"可部署在高校"目前不成立。** 监听地址与 Host 白名单硬编码，且 `/api/bootstrap` 无鉴权下发令牌——单机可用，多用户即等于全部项目裸奔。
4. **最基础的码表管理缺失。** 不能改名、删除、合并编码，无法删除文档，也没有编码层级。这会真实地卡住研究流程。

**给团队的一句话建议：** 你们已经证明了"能用"，接下来要证明的是"敢用"——而"敢用"取决于数据是否真的不出本地、以及多人协作时是否真的隔离。把本地推理和访问控制这两件事做扎实，这个项目就从"一个不错的课程作业"变成了"实验室真的会部署的工具"。绘图工作台很性感，但它是加分项，不是及格线。
