# QualiCraft 开发流程规范

**版本：** v1 · 2026-10-06
**作用：** 规范每次开发的动作顺序，并记录当前的设计原则与状态。
**配套：** 与 `研究计划.md`（PRD v2.0）配合使用——那份说「做什么」，这份说「怎么做、做到哪了」。

---

## 0. 这份文档怎么用

**每次开工前，按顺序读三样东西：**

1. `研究计划.md` —— 确认这次要做的事在 PRD 里有没有依据
2. **本文档第 1 节**（开工检查清单）
3. **本文档第 5 节**（当前状态快照）—— 确认起点

**每次收工后，更新第 5 节。**

> 规则：**任何改动都要能回答「它在 PRD 的哪一条，或者它是对 PRD 的哪一次细化」。** 答不上来的，先别做。

---

## 1. 开工检查清单

```
□ 1. 读了 研究计划.md，确认这次的任务有依据
□ 2. 读了本文档第 5 节，确认当前状态和上次留下的待办
□ 3. 仓库状态：git status 干净？在正确的分支上？
□ 4. 服务状态：8765（应用）/ 9111（桩模型）是否需要启动？
□ 5. 本次任务范围：写下来（一到三句话），范围外的先不做
□ 6. 验证方式：这次改完，怎么证明它有效？（测试 / 截图 / 实测数据）
```

**第 5 条特别重要。** 本项目的最大风险不是做不出来，而是**范围蔓延**——同时动五件事，结果五件都没做完。

---

## 2. 开发流程

```
① 定范围      写下一到三句话，明确这次做什么、不做什么
② 实现        小步改，每步跑一次语法/测试检查
③ 自测        用真实数据实测，不只看代码「应该对」
④ 验证        跑测试套件 + 语法检查 + 实际截图或数据佐证
⑤ 提交        一个逻辑改动一个提交，提交信息写清「为什么」
⑥ 更新文档    更新本文档第 5 节；如果偏离了 PRD，补进第 6 节
```

**关于第 ③ 步**：本项目的经验是——**问题都是「用」出来的，不是「想」出来的**。上一轮你提出的三个缺口（高亮没颜色、批注框位置、不能输入关键字建码），全部来自实际使用，没有一条来自设计评审。

**关于第 ④ 步**：每次必须跑的验证：

```bash
python -m unittest discover -s tests    # 后端（当前 23 项）
node --check web/app.js                 # 前端语法
# CSS 括号配平
python -c "c=open('web/style.css').read();print(c.count('{')==c.count('}'))"
```

## 3. 积木设计：把复杂度移到结构里

### 3.1 设计原则（来自 Pi Agent 与 Instinct）

> **Pi**：框架应该轻，复杂度由**模型**承担 → 所以核心只有 418 行，只有一个「我们没做什么」清单。
> **Instinct**：界面应该消失，复杂度由**数据结构**承担 → 所以没有独立 App，记忆是 Git 管理的 Markdown。

**共同原理：把复杂度从用户身上，移到结构里。**

对 QualiCraft 的具体含义：**用户只做三件事——读、标、看规律。其余一切都该由结构承担。**

### 3.2 三层结构

#### 第一层：核心（不可关闭）

没有这三样就不是定性分析工具：

| 核心 | 内容 |
| :--- | :--- |
| **文档** | 转录稿文本 + 字符坐标 |
| **编码** | 名称、颜色、在码表中的位置 |
| **标注** | 片段 → 编码 的对应关系 |

#### 第二层：能力块（可开可关）

| 能力块 | 提供什么 | 默认 |
| :--- | :--- | :--- |
| **主题归组** | 码表树、层级、拖拽 | 开 |
| **备忘录** | 文档级 / 编码级 / 主题级笔记 | 开 |
| **AI 建议** | 建议队列、采纳/拒绝、引文溯源 | 开 |
| **频次分析** | 编码频次、文档 × 编码矩阵 | 内容分析开 |
| **交叉表** | 类别 × 文档属性 | 内容分析开 |
| **信度** | 多编码者、Kappa / Alpha | 内容分析开 |
| **绘图** | 共现热力图、桑基图、气泡图 | 关 |
| **审计与导出** | 审计轨迹、CSV / JSON / REFI-QDA | 开 |

**交互方式**：侧栏底部一个「工具」入口，列出全部能力块，每个一个开关。关掉 = 界面上完全消失。

#### 第三层：预设组合（工作流模式）

| 模式 | 组合 |
| :--- | :--- |
| **内容分析** | 核心 + 频次 + 交叉表 + 信度 |
| **主题分析** | 核心 + 主题归组 + 备忘录 |
| **扎根理论** | 核心 + 主题归组 + 备忘录 + 三阶段标记 |
| **通用** | 核心 + 备忘录 |

用户也可以自己组合并保存为自定义模式。

### 3.3 为什么用「渐进出现」而不是「配置面板」

纯粹的配置面板有个问题：**新用户打开会一脸茫然**——他不知道自己该开哪个。

所以建议是**混合**：

- **默认渐进出现**：你建了第一个子编码，码表树自动展开层级；你连了模型，建议队列出现；你有 ≥2 个编码，频次分析出现
- **同时提供显式开关**：熟练用户可以钉住/隐藏任意块

**关键：默认永远是最少的。** 这是 Pi 的做法——默认 4 个工具就够用，要更多自己去装。

### 3.4 落地建议：分两步，不要一次做完

| 步骤 | 内容 | 风险 | 状态 |
| :--- | :--- | :--- | :--- |
| **第一步** | 只做「显式开关」：侧栏加工具面板，能力块能开能关，状态存项目里 | 低 | ✅ **已完成** |
| **第二步** | 再做「渐进出现」：根据状态自动显示/隐藏 | 中（要小心别让用户困惑） | ⬜ 未开始 |

**第一步已落地**：侧栏底部「Capability blocks」入口，6 个块可独立开关，状态存进项目（`project["blocks"]`，schema v4）。关掉的块**从界面上完全消失**，不是变灰。

> **重要更正**：我最初把 `NOT_BUILDING.md` 理解成「永久不做」，并据此砍掉了绘图工作台。**这是对 Pi Agent 的误读**——它的 "What we didn't build" 意思是「没内置」，每一项都有扩展路径（官方有 50+ 扩展示例）。
>
> 已按三层重写：**核心**（不可关）/ **可选块**（都在，默认不装，点击添加）/ **真正不做**（只有 4 条，且都是方法论立场）。
>
> **绘图工作台是可选块，不是被砍掉的功能。**

## 4. 研究流程 × 工具支持对照

以主题分析（Braun & Clarke）六阶段为准，**逐阶段核查当前代码**：

| 阶段 | 工具支持 | 证据 |
| :--- | :--- | :--- |
| **1 熟悉数据** | ✅ **已补** | 文档有 `memo` 字段，阅读区顶部有 READING NOTES 笔记条，输入即自动保存 |
| **2 开放编码** | ✅ 好 | 内联批注框 + 关键字建码 + 回车即打标 |
| **3 搜寻主题** | ✅ 可以 | `parent_id` 支持多层归组（app.js 中 11 处） |
| **4 审查主题** | ⚠️ 部分 | 能改父级 / 合并 / 删除，但**没有专门的审查视图**（看不到"哪些编码还没归组"） |
| **5 界定命名主题** | ✅ 好 | 编码有 `definition / memo / anchor_examples / inclusion / exclusion / status` 六个字段 |
| **6 撰写报告** | ✅ **已补** | `methods_narrative()` 从项目状态 + 审计轨迹生成 Markdown 方法学记录，导出菜单第 4 项 |

**结论：六阶段里 4 个做好，1 个可以做，1 个部分。**

**剩下的缺口：**

1. **阶段 4 缺审查视图**——需要"哪些编码还没归入主题"的提示。这是主题分析第 3–5 阶段的核心进度指示器。
2. **能力块开关**——Pi 式「搭积木」的落地（第 3.4 节）
3. **缺口 4：码表拖拽**

> 阶段 6 已落地。这是「QualiCraft 比 ATLAS.ti 好在哪」的直接答案——ATLAS.ti 也不会帮你写方法学章节。
