# 设计理念与下一步方向

**日期：** 2026-10-06
**触发：** 关于「与 ATLAS.ti 的差距」「是否有执行框架」「从 Pi Agent / Instinct 借鉴什么」的讨论

---

## 一、离 ATLAS.ti 到底有多远

### 诚实评估：差距有两个维度，性质完全不同

| 维度 | 差距 | 能不能追 |
| :--- | :--- | :--- |
| **功能广度** | 巨大。ATLAS.ti 有 30+ 年积累：多媒体编码、音频转写、IRR、网络图、词云、团队协作、REFI-QDA、教学资源、文献引用生态 | **追不上，也不该追** |
| **操作手感** | 中等，但**是可追的** | **能追，而且成本不高** |

**你觉得"差距很大"，主要来自第二类，不是第一类。** 证据是：你上一轮提出的问题全都是手感问题（高亮没颜色、批注框位置不对、不能输入关键字建码），没有一条是"缺某个高级功能"。

**这意味着好消息**：让你觉得"不好用"的东西，恰好是改动成本最低的东西。

### 我的核心判断：不要做"更差的 ATLAS.ti"

两个人对几十个工程师做了 30 年的产品做功能对标，是必输的仗。而且**赢了也没意义**——你追到 80% 的功能，用户为什么不直接用 ATLAS.ti？

真正该问的是：**ATLAS.ti 做不到什么？**

| ATLAS.ti 做不到的 | QualiCraft 的天然优势 |
| :--- | :--- |
| 让你看清 AI 到底改了什么、凭什么 | 每条建议都锚在字符坐标上，可溯源、可拒绝 |
| 把方法学过程变成可 diff 的文本 | 本地文件，你拥有它 |
| 让伦理委员会读源码验证数据流向 | MIT 开源，可审计 |
| 跑在一台不联网的笔记本上 | 零依赖，纯标准库 |

**这四件事里没有一件是"功能"，全都是"结构"。** 这是本项目的立足点。

### 但有一个前提必须承认

现在的 UI 是一个**能跑的原型**，不是产品。三栏布局 + 胶囊标签是学到了 ATLAS.ti 的形，但"手感"来自几千个微决策（间距、动效、键盘流、错误提示的语气）。**这些东西没法一次设计出来，只能靠反复用。**

所以我的建议不是"继续加功能"，而是——见第五节。

## 二、项目现在有完整的执行框架/研究流程吗

### 诚实回答：**没有。**

现状是**一组功能**，不是**一条流程**：

- PRD 描述的是**模块**（A 解析 / B 工作台 / C 绘图 / D 导出），不是**流程**
- 工具里没有"阶段"概念——打开就是一片文档和一个空码表，不告诉你现在该干什么
- 没有"项目章程"——研究问题、方法选择、编码手册这些**方法论资产**没有地方安放
- 编码完成后，**没有任何东西帮你写出方法学章节**

### 一个研究流程实际长什么样

以主题分析（Braun & Clarke）为例：

```
1 熟悉数据      → 通读、写初步笔记
2 开放编码      → 逐段打标签（不预设码表）
3 搜寻主题      → 把编码归组
4 审查主题      → 合并/拆分/丢弃
5 界定命名主题  → 写主题定义 + 锚例
6 撰写报告      → 方法学章节 + 结果
```

**现在的工具只在第 2 步和第 3 步（部分）可用。** 第 1、4、5、6 步没有任何支撑。

### 我认为这才是"不够好"的深层原因

不是因为少了某个按钮，而是**工具不知道你在哪一步**。所以它只能把所有东西同时摊开，让用户自己找。

### 怎么补：不是加四个模块，而是加"阶段感"

我在方法论文档里提过「工作流模式」，这里把它说得更具体：

**最小可行版本（三件事）**

1. **项目章程（Project Charter）**——项目建好先填一页：研究问题、方法（内容分析/主题分析/扎根理论）、数据来源、伦理批件号。这一页**会自动注入 AI 提示词**，也**会跟着数据一起导出**。
2. **阶段指示器**——侧栏顶部显示当前阶段 + 一句"下一步做什么"。阶段可以手动切换，也可以由工具根据状态推断（比如"还有 12 个编码没归入主题"）。
3. **方法学副产品**——每个阶段结束时，工具生成一段可编辑的 Markdown：编码过程、主题演化、决策记录。**写论文时直接用。**

第 3 点是我认为最被低估的价值。研究者的真实痛点不是"编码不够快"，而是**"我做完分析，还要花两周回忆自己是怎么做的，才能写出方法学章节"**。

## 三、从 Pi Agent 借鉴什么

Pi 是 Mario Zechner 写的极简终端编码代理，**核心循环只有 418 行**，GitHub 84K stars。

### 最值得学的一条：它有一个「我们没做什么」页面

发布页通常堆功能列表，Pi 反其道而行，专门列出**刻意不做**的事：

- 没有内置 MCP 协议
- 没有子代理
- 没有权限确认弹窗
- 没有计划模式
- 没有内置任务列表

**设计假设**：现代模型已经经过大量 RL 训练，本身就知道该怎么做，所以框架越轻越好。

### 为什么这条对 QualiCraft 特别重要

因为它直接回答了你"大道至简"的诉求，而且给了一个**可执行的形式**：

> 写一份 `NOT_BUILDING.md`，明确列出 QualiCraft **不做**什么。

比如：

- ❌ 不做多媒体编码（图片/音频/视频）——那是 ATLAS.ti 的地盘
- ❌ 不做实时多人协作——本地单机是特性，不是缺陷
- ❌ 不做云端账号体系
- ❌ 不做通用绘图引擎（R/Python 沙箱）——**只做 3 张图，做到能发表**
- ❌ 不做词云、不做网络图
- ❌ 不做"自动编码"——只做"建议 + 人工裁决"

**这份清单有三个作用**：
1. 防止功能蔓延（你现在的最大风险）
2. 汇报时极其有力——导师会问"为什么不做 X"，你有答案
3. 让"轻"变成**主动选择**而不是**能力不足**

### 其他可借鉴的

| Pi 的做法 | 对应到 QualiCraft |
| :--- | :--- |
| 只给模型 4 个工具（read/write/edit/bash） | 核心动作只有 3 个：划选 → 打标 → 归组。其他都是辅助 |
| 系统提示 < 1,000 tokens | 现在发整个码表 + 整段文本，可以再瘦 |
| **AGENTS.md 分层配置注入提示词** | **项目章程注入提示词**——让 AI 按你的编码手册编码，而不是按它自己的理解 |
| 树状会话历史（可回溯、可重试） | 编码决策应该可撤销、可回溯（现在只能删，不能撤销） |
| 扩展层而非内置 | 先把核心做扎实，别急着做插件系统 |
| 会话中途切模型 | 已有（OpenAI 兼容端点） |

## 四、从 Instinct 借鉴什么

Instinct 是 2026 年的个人 AI 助理，**没有独立 App**——你直接在 iMessage / WhatsApp 里跟它说话。创始人 Noah Shinn（23 岁，NeurIPS《Reflexion》一作），14 名员工，估值 100 亿美元。

### 4.1 创始人有一条早期原则，非常值得抄

> **"不先聚焦能力，只聚焦可理解性。"**

用户不需要学新界面、不需要配置工作流，只要用自然语言交代目标。超过 50% 的流量甚至不走自己的通道，而是借道 iMessage。

**映射到 QualiCraft**：现在的界面在**教你它的概念**（Codebook、Margin、Insights、Audit trail、Schema v2、工作流模式……）。研究者不想学这些。他想的是：

> "我有一份访谈，我想标出重要的地方，然后看看有什么规律。"

**"可理解性"意味着**：打开就能开始，不需要读文档；界面上的词是研究者的词（主题、编码、引文、备忘录），不是工程师的词（schema、offset、review queue）。

### 4.2 最值得抄的一条：它的记忆架构

这是我认为**整场讨论里最有价值的一个点**。

Instinct **不把聊天记录原样塞回上下文**。它的做法是：

- 长期信息整理成**一套 Git 管理的 Markdown 文件**
- 每次对话开始只加载约 **4,250 tokens** 的用户状态摘要
- 更细的偏好用**类 grep 的关键词搜索**检索，**不用向量/语义检索**
- 后台进程**每天跑一次**：整理临时信息、总结长期偏好、**用新事实修正旧信息**
- **用 Git 保留版本历史**

### 为什么这条对 QualiCraft 是革命性的

现在 QualiCraft 的项目是：**SQLite 里一个不透明的 JSON blob**，审计轨迹是 blob 里的一个数组。

**改成 Instinct 那样会怎样：**

```
项目文件夹/
├── 章程.md              ← 研究问题、方法、伦理批件号
├── 码表.md              ← 人可读、可手改、可 diff
├── 编码/
│   ├── I1.md            ← 每段引文一行，可 grep
│   └── I2.md
├── 备忘录/
│   ├── 主题-数据共享.md
│   └── 方法反思.md
└── .git/                ← 审计轨迹 = Git 历史
```

**这一改动带来四件事：**

1. **"可审计"从功能变成结构**——不再需要"审计轨迹"这个功能，Git 历史本身就是。而且它**不可篡改、可 diff、带时间戳**，正是伦理委员会和期刊要的。
2. **研究者可以直接读和改**——码表是 Markdown，他可以用任何编辑器改，不需要学你的界面。
3. **方法学章节自动生成**——`git log 码表.md` 就是"主题如何演化的"完整叙事。
4. **grep 而非向量**——研究者的检索需求是精确的（"所有关于数据共享的引文"），不是模糊的。而且**可解释**：你知道为什么这条被找到。

**这正好是我在第一次评估里说的那个差异化**（"AI 编码过程可审计"）——但当时它只是个功能，现在它可以变成**架构**。

### 4.3 其他可借鉴的

| Instinct 的做法 | 对应到 QualiCraft |
| :--- | :--- |
| 零摩擦：不学新界面 | 打开即用，概念用研究者的语言 |
| **从"给答案"到"给结果"** | 从"给你一个编码工具"到"给你一份可投稿的方法学章节" |
| 授权以用户舒适的速度进行，随时可撤回 | AI 请求预览已经做到了，可以再进一步：**按项目记住授权范围** |
| 主动触发（邮件到达、日历变动时唤醒） | 不适用（研究工具不该主动打扰），但**"还有 12 个编码没归组"这种提示**是对的 |
| 信任前置 | 本地 + 开源 + 可读文件，信任是**结构给的**，不是承诺给的 |

## 五、三个参照物交汇出的一个核心思想

把 Pi 和 Instinct 放在一起看，它们其实在说同一件事：

> **Pi**：框架应该轻，因为复杂度应该由模型承担，而不是由用户承担。
> **Instinct**：界面应该消失，因为复杂度应该由数据结构承担，而不是由用户承担。

**共同的原理：把复杂度从用户身上，移到结构里。**

这对 QualiCraft 意味着什么？

### 现在的做法（复杂度在用户身上）

- 用户要理解：码表、层级、标注、建议队列、审计轨迹、工作流模式……
- 用户要记住：哪个编码归哪个主题、哪些建议还没审、上次改了什么
- 用户要自己拼：方法学章节、主题演化叙事、决策依据

### 应该的做法（复杂度在结构里）

- 用户只做三件事：**读、标、看规律**
- 其他一切都由数据结构承担：
  - 层级 → 码表文件的结构
  - 审计 → Git 历史
  - 方法学章节 → `git log` 的输出
  - AI 一致性 → 章程文件注入提示词

### 一句话总结我的想法

> **QualiCraft 不该是一个"功能更多的定性分析工具"，而该是一个"让研究过程本身成为可读文本的工具"。**
>
> 前者跟 ATLAS.ti 比广度，必输。
> 后者 ATLAS.ti 做不了——因为它的数据模型是封闭的二进制工程文件。

## 六、具体建议的下一步

### 我的建议顺序（和之前的建议有调整）

| 顺序 | 做什么 | 为什么 |
| :--- | :--- | :--- |
| **1** | **你自己用一周** | 拿你真实的访谈数据跑一遍完整流程。上一轮那 3 个缺口，全都是你用出来的，不是我设计出来的。**这是最高效的改进来源。** |
| **2** | 补完手感（缺口 4 拖拽 + 细节打磨） | 结构已经对了，剩下是手感 |
| **3** | 写 `NOT_BUILDING.md` | 成本极低，收益极高（防蔓延 + 汇报用） |
| **4** | 项目章程 + 阶段指示器 | 让工具"知道你在哪一步" |
| **5** | **把项目存储改成 Git 管理的文本文件夹** | 这是最大的架构决策，但也是最大的差异化。建议先做个小原型验证 |
| **6** | P1（交叉表/信度） | 分析功能。等前面稳了再做 |

### 关于第 1 条，我想强调一下

你说"是否现在按照研究流程进行呢"——**我认为应该，但不是"设计好流程再用"，而是"用起来，让流程自己浮现"。**

Pi 的作者只写了 418 行，因为他知道模型已经会了，不需要他教。同理：**你不需要先设计出完美的工作流，你需要先用真实数据撞出真实的需求。**

上一轮你提出"不能输入关键字建码"——这不是设计出来的，是用出来的。**再给我一周的真实使用反馈，比我现在猜十个功能都有用。**

### 关于第 5 条，风险提示

把存储从 SQLite JSON 改成 Git 文本文件夹，是一次**大手术**：

- 好处：可审计成为结构、方法学章节自动生成、研究者可直接编辑
- 代价：性能（现在已有 9.6MB 整包重写的隐患）、并发、迁移
- **建议先做最小原型**：只把"码表"和"审计"改成文本 + Git，引文偏移仍留在 SQLite。验证概念后再全量迁移。

## 附：这次讨论的三个结论

1. **离 ATLAS.ti 的差距主要在"手感"，不在"功能"**——而手感是能追的，功能广度不该追。
2. **项目目前没有研究流程，只有功能集合**——缺的是"阶段感"和"方法学副产品"，不是更多模块。
3. **Pi 和 Instinct 共同指向一个思想：把复杂度从用户身上移到结构里。** 对 QualiCraft 最具体的一次落地，就是**让项目存储变成 Git 管理的可读文本**——那样"可审计"就不再是功能，而是架构本身。
