关于本次走查中「AI 模型」的说明（请务必先读）：
本次演示把模型端点指向了一个本地桩程序（http://127.0.0.1:9111/v1，模型名 local-stub-model），它按关键词规则从原文中挑选真实子串作为引文并返回编码建议，内部不含任何语言模型。这样做是为了在不需要 API key、不产生费用、不把数据发出本机的前提下，完整演示「请求预览 → 确认发送 → 建议审核 → 采纳/拒绝」这条链路。
界面与流程与接真实模型（云端 Qwen 或本地 Ollama/vLLM）完全一致，只是返回内容的质量不同。截图中的 local-stub-model 字样即为此意。

阶段一 · 建立项目并导入转录稿

平台是一个本地 Web 应用。打开 http://127.0.0.1:8765 即可，无需安装任何依赖。

1

打开平台

启动后会自动打开最近使用的项目（此处为内置的虚构演示项目，含示例编码与待审建议）。左侧是项目/文档/码表导航，中间是阅读与编码区，右侧是 AI 建议审核区。左下角常驻提示 “Local workspace · Cloud only when requested”。

启动后的默认界面（演示项目）。左侧项目下拉框可切换到其他项目

2

新建项目

点左侧 “+ New / import project”，弹窗里输入项目名并创建。同一个弹窗里还可以导入 TU Delft 盲测集 / 参考集、Tian 2021 数据集，或恢复项目 JSON 备份。

项目对话框：新建、切换、导入基准数据集、恢复备份

3

填写项目名

本次使用「走查演示 · 架构与代码关系」。

输入项目名称

4

项目已创建（空工作区）

新项目是干净的：0 文档、0 编码、0 待审核。中间会提示可以从导入一份访谈开始。

空项目状态

5

导入转录稿

点 “Import interview”。支持 TXT / DOCX，也可以直接粘贴文本。下方提示了说话人标签的写法（Doctor:/Patient:、Interviewer:/Participant:、IQ.../IP1:），中文标签如 医生：/患者： 同样支持。

导入对话框：选文件 / 命名 / 或直接粘贴

6

选择 DOCX 文件

本次选的是真实研究数据 Interview Transcript_IP6.docx（25,125 字节）。文件选中后文档名会自动填充。

已选中 DOCX，文件名自动填入

7

转录稿导入完成

DOCX 被解析成 10,159 字符 / 72 段。可以看到 DOCX 里的访谈提纲、人口学问题、IQ1.1: 提问与 Answer: 回答都被正确还原，提问被识别为斜体（说话人区分生效）。

转录稿已加载，右侧显示 10,159 字符 · 72 segments · 0 codings

导入时会计算文档的 SHA-256 校验和并写入审计轨迹，后续每次校验都能确认原文未被篡改。

阶段二 · 建立码表

码表是定性研究的核心工具。每个编码有名称、定义、颜色。本次针对这篇访谈建立了 6 个编码。

8

新建编码

点 “+ New code”，填写编码名、定义与颜色。定义栏的提示语是「Describe when to use this code and when to exclude it」，即要求写明纳入与排除标准。

新建编码：名称 / 定义与纳入标准 / 颜色

9

码表建立完成

6 个编码全部就位，左侧码表显示各自的色块与当前引用计数（此时均为 0）。

码表：Model-driven code generation、Architecture-code traceability、Consistency verification、Code readability and comprehension、Change propagation、Tooling and automation

阶段三 · 人工编码（核心步骤）

这是本次走查的重点，也是之前被 Bug 卡住的环节。

10

划选文本 → 出现打标工具条

在正文里拖选一段文字，阅读区底部立即出现工具条：「Selected 85 characters / Apply code / Analyze selection」。被选中的文字有蓝色高亮。

选中 85 个字符，底部出现 Apply code 工具条

这里就是之前修复的 Bug。修复前，这个工具条被 CSS 的 position:sticky 困在一个只有自身高度的容器里，导致它停留在 15,055 像素高滚动内容的绝对底部——当你选中文档中部的文字时，按钮在可视区下方约 14,676 像素处，所以「看不到添加编码的界面」。修复方式是让 sticky 的约束容器变成真正的滚动容器。
11

打标对话框

点 “Apply code”。弹窗顶部回显你选中的原文，下面是编码下拉框与研究备忘录输入框。

回显引文 + 选择编码 + 写备忘录

12

打标成功：高亮 + Margin 胶囊标签

保存后，正文对应片段出现黄色高亮，右侧边缘栏出现胶囊标签，标注编码名与来源 HUMAN。左侧码表计数同步 +1。

高亮 + Margin 标签（HUMAN = 人工编码）

来源标识共有四种：HUMAN（人工）、AI · REVIEWED（AI 建议经人工采纳）、REFERENCE（导入的参考标注）、以及 AI 建议的待审状态。这让「哪些是机器提的、哪些是人定的」在界面上永远可辨。
13

继续编码：多条编码并存

重复上述操作，对多个片段打上不同编码。可以看到一段文字可以同时承载多个编码（第 25 段同时有 Model-driven code generation 与 Tooling and automation 两个标签）。

7 条编码分布在不同段落，左侧码表计数实时更新

14

点标签查看引文与备忘录

点任意胶囊标签，可以查看该编码的原文引文、字符区间、来源，并编辑研究备忘录，也可以删除这条编码（删除记录会保留在审计轨迹里）。

编码详情：引文 + 来源区间 + 备忘录编辑 + 删除

阶段四 · AI 辅助编码

QualiCraft 的 AI 不是「自动编码」，而是「提出建议、由研究者裁决」。整条链路有强制的数据出境确认。

15

设置模型端点

点右上角 “Model”。可填任意 OpenAI 兼容端点。关键点：填 http://127.0.0.1:... 即接入本地模型，无需 API key，数据不出本机。本次指向本地桩程序。

端点 / 模型名 / API Key 三项设置

界面上明确写着：Manual coding is free and works offline. Cloud analysis runs only after confirmation and may incur provider charges. 另外，API key 只保存在服务端内存，不会进入项目文件、浏览器存储、请求预览或任何导出。
16

发起 AI 分析

点 “Analyze with AI”。可选编码方法（演绎：只允许使用已有编码 / 归纳：允许提出新编码）与分析范围（仅受访者发言 / 全部段落 / 当前选区）。勾选是否附带上一轮提问作为上下文。

编码方法 + 分析范围 + 上下文开关

17

发送前的请求预览（强制确认）

这一步是 QualiCraft 相对商业工具最值得保留的设计。发送前必须点 “Preview requests”，弹窗列出：目标端点、模型名、请求数量、目标字符数，并可展开查看每一个请求的完整 JSON 正文。

本次：http://127.0.0.1:9111/v1 · 31 requests · 4,765 target characters

这里展示的是本次真实的预览内容：31 个请求、4,765 个目标字符。经检查，预览中不包含 API key（已做程序化校验）。发送按钮在勾选「I have reviewed the content」之前是禁用状态。
18

勾选确认，按钮激活

必须显式勾选「这些文本已去标识化，且允许发送给该服务商」，发送按钮才会从禁用变为可用。

确认后才可发送

19

分析完成：建议进入审核队列

31 段全部处理完毕，产出 13 条待审建议。每条建议卡片包含：编码名、编码定义、原文引文、字符区间 [2081, 2179)、可点击的 Locate 溯源链接、以及提出该建议的理由。

顶部进度条：Analysis complete · 31/31 segments · 13 new suggestions

反幻觉机制：服务端会校验模型返回的引文必须是原文中精确且唯一可定位的子串，否则该建议直接丢弃、不进入队列。点 “Locate ↗” 会让中间阅读区平滑滚动并闪烁对应文本，实现 100% 溯源。建议不会自动变成正式编码，必须由研究者逐条采纳。
20

采纳建议 → 转为正式编码

点 “Accept coding” 后，该建议变成一条正式编码，来源标记为 ai_reviewed，并自动定位到原文。也可以点 “Reject” 拒绝，拒绝记录同样留在审计轨迹中。

采纳后编码数 7 → 8，其中 ai_reviewed 1 条；待审 13 → 12

本次走查演示了两种裁决：采纳 1 条、拒绝 1 条。拒绝的编码不会进入码表，但决策被记录，便于日后复核。

阶段五 · 分析、溯源与导出

21

Insights：编码频次与文档×编码矩阵

左侧导航 “Insights”。上方是各编码的引用频次条形图，下方是文档 × 编码计数矩阵。

编码频次 + 文档 × 编码矩阵

这里也是当前能力的天花板。Insights 只有频次条形图与计数矩阵，没有共现热力图、没有桑基图、没有混合研究气泡图、没有参数化绘图控件——PRD 中定义为「核心杀手锏」的绘图工作台尚未实现。此外这里只有原始计数，没有百分比，也没有交叉表与信度。
22

审计轨迹

左侧 “Audit trail”。每一次导入、建码、打标、AI 分析、建议裁决都被完整记录并带时间戳，随项目一起导出。

完整活动日志（可展开查看每条记录的完整 JSON）

23

导出

走查结论

已经跑通的部分

  • 新建项目、项目切换、备份恢复
  • 真实 DOCX 导入并正确还原结构与说话人
  • 码表建立（名称 / 定义 / 颜色）
  • 划选打标、高亮、Margin 胶囊标签、备忘录
  • 编码来源区分（人工 / AI 采纳 / 参考）
  • AI 请求预览与强制确认、引文反幻觉校验
  • 建议审核队列（采纳 / 拒绝）
  • 频次统计、文档×编码矩阵
  • 完整审计轨迹
  • 三种格式导出

走查中确认缺失的部分

  • 编码不能改名、删除、合并；文档不能删除
  • 码表没有层级（编码无法归组成主题）
  • 编码只有单一 definition 字段，没有锚例 / 纳入 / 排除标准的独立字段
  • 文档没有属性字段，无法做交叉表
  • 无多编码者概念，无编码者间信度
  • 无共现矩阵、无主题地图、无参数化绘图工作台
  • 频次只有原始计数，无百分比
  • 无音频转写、无 PDF 导入、无 REFI-QDA 互通
