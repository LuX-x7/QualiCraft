# QualiCraft 方法论支持评估与设计方案

**评估对象：** QualiCraft（提交 `1de32e3`）
**评估问题：** 当前项目是否支持内容分析（Content Analysis）与主题分析（Thematic Analysis）？如何按两种方法的操作流程设计以完成转录稿编码任务？
**日期：** 2026-09-27

---

## 结论先行

**当前项目两种方法都不完整支持。** 它实现的是两种方法共享的**最低公分母**——"文本片段 → 贴标签 → 计数 → 导出"。但两种方法各自的**核心装置**都缺失：

- **主题分析被"码表无层级"直接卡死。** 主题分析的核心动作是"从编码到主题"，而当前码表是一个扁平数组，没有任何父子结构，研究者无法把编码归组成主题。
- **内容分析被"无信度计算 + 无案例属性模型"卡死。** 内容分析需要编码者间信度，以及"类别 × 受访者群体"的交叉表；当前既没有多编码者概念，文档也没有任何属性字段。

**关于你的判断——"按两种方法的操作流程设计就能完成编码任务"——我想提出一个更精确的版本：**

编码这个**动作**现在已经能做了（我把阻塞的 bug 修好了，见另一份补丁）。两种方法的流程设计不会改变"能不能编码"，它改变的是**编码之后能不能支撑方法学要求**。

所以关键区别在这里：

| | 主题分析需要 | 内容分析需要 |
| :--- | :--- | :--- |
| 编码动作 | 归纳式开放编码 | 演绎式套用既定类别 |
| **编码之后** | **把编码归组成主题（层级）** | **统计类别频次 + 检验信度** |

**而这两种"编码之后"的需求，可以建立在同一个底层结构上。** 我建议不要按"两种方法"分叉开发两套功能，而是做一个**共享底座 + 工作流模式切换**。理由在第五节展开——这样工作量小得多，也不会把代码库分裂成两半。

## 一、两种方法（外加必须考虑的第三种）的操作流程

### 1.1 内容分析（Content Analysis）

主流有两支，但操作装置高度重叠：

**Mayring 的定性内容分析（8 步）**
1. 提出研究问题 → 2. 界定类别 → 3. **制定编码议程（coding agenda）** → 4. 试编码 → 5. 修订类别 → 6. 正式编码 → 7. 频次分析 → 8. 信度检验与报告

**Krippendorff 的量化内容分析**
单元化（unitizing）→ 抽样 → 编码 → **信度检验** → 推断

两支共同要求的装置：

| # | 装置 | 说明 |
| :--- | :--- | :--- |
| 1 | 预定义类别系统 | 类别有名称、定义、**锚例（anchor examples）**、**纳入/排除规则** |
| 2 | 系统化编码 | 全部文本按同一套规则编码（非选择性） |
| 3 | 频次统计 | 类别频次 + 百分比 + 总数 |
| 4 | **编码者间信度** | Cohen's κ（两人）/ Krippendorff's α（多人） |
| 5 | **交叉表** | 类别 × 案例属性（如"类别 × 受访者角色"） |
| 6 | 类别层级 | 主类别 → 子类别（至少两级） |

### 1.2 主题分析（Thematic Analysis）

**Braun & Clarke 的反身性 TA（6 阶段）**
1. 熟悉数据 → 2. **生成初始编码** → 3. **搜寻主题** → 4. **审查主题** → 5. **界定与命名主题** → 6. 撰写报告

必需装置：

| # | 装置 | 说明 |
| :--- | :--- | :--- |
| 1 | 归纳式编码生成 | 从数据中长出编码，不预设 |
| 2 | **编码 → 主题的层级归组** | **核心中的核心**，第 3–5 阶段全靠它 |
| 3 | 主题定义与改名 | 主题是演化的，必须能反复改 |
| 4 | **备忘录** | 编码级、主题级、数据集级；备忘录是分析本身 |
| 5 | 主题审查 | 合并、拆分、降级为编码 |
| 6 | 主题地图 | 主题之间关系的可视化 |
| 7 | 审计轨迹 | 主题如何演化出来的可追溯 |

> **注意一个方法论分歧：** 反身性 TA 明确**不要求**（Braun & Clarke 甚至反对）编码者间信度——它把研究者主体性视为分析资源而非误差。所以信度功能必须是**可选**的，不能默认开启。这一点直接影响设计。

### 1.3 扎根理论（Grounded Theory）—— 必须考虑，因为你们的数据集就是它

不能只考虑两种方法，理由很实在：

- **Tian 2021 数据集本身就是扎根理论数据集**（`Grounded_Theory_Interview_Examples_Tian_2021`）。
- **TU Delft 数据集**据你们自己的 `GUIDE_DATA_AUDIT.md` 记载，用的是"理论驱动标签 + 开放/主轴/聚焦编码"的混合策略。

流程：开放编码 → 主轴编码 → 选择性编码 → 理论饱和

必需装置：三级编码**阶段标记**、持续比较、饱和追踪。

## 三、核心诊断：为什么"码表无层级"是致命的

当前编码对象（`core.py:83` `add_code`）：

```python
code = {"id": uid(), "name": name, "definition": definition, "color": color}
```

**没有 `parent_id`。** 这意味着研究者能做的只有"给文本片段贴标签"，无法"把标签归组成主题"。

对主题分析来说，这不是"少了个锦上添花的功能"，而是**核心动作无法执行**。Braun & Clarke 的第 3–5 阶段（搜寻主题、审查主题、界定与命名主题）全部依赖"把编码组织成主题"这个操作。没有层级，研究者只能：

- 把主题也做成一个编码，然后**靠脑子和外部 Excel 记住哪些编码属于哪个主题**——分析一旦超过 20 个编码就会失控；
- 或者**把主题写进编码名**（这正是 TU Delft 研究者做的事，见下一节）。

## 四、一个意外的实证：TU Delft 码表把层级"藏"在了编码名里

我把真实的 TU Delft 码表（54 个编码）做了结构化分析，结果很能说明问题：

```
=== 编码名中的角色后缀分布 ===
  (无角色后缀)      27 个
  R                14 个
  PM/SP            13 个

=== 同一语义主题同时存在两种角色版本的主题数: 13 ===
  4TU: reusing research data          -> PM/SP + R
  4TU: sharing research data          -> PM/SP + R
  Data Steward                        -> PM/SP + R
  Experience with DMPs                -> PM/SP + R
  Experience with RDM                 -> PM/SP + R
  Experience with infrastructures     -> PM/SP + R
  ...

推断：语义主题总数（剥离角色维度后）= 41
原始平铺编码数                        = 54
```

**这说明了三件事：**

1. **真实的码表天然是二维的**：`语义主题`（41 个）× `受访者角色`（PM/SP = 政策制定者/支持人员，R = 研究者）。

2. **研究者被迫把"案例属性"塞进了编码名。** `[PM/SP]` 和 `[R]` 本质上不是编码，而是**受访者的属性**。他们之所以这么做，正是因为原始工具**没有案例/属性模型**——这是没有属性功能时的经典权宜之计。

3. **QualiCraft 现在把这份结构化信息拍平成了 54 项列表。** 于是研究者无法：
   - 把"所有关于 Experience with RDM 的编码"（两种角色）汇总看；
   - 做"主题 × 角色"的交叉表——**而这恰恰是内容分析最核心的输出**。

**这个案例同时证明了第五节两个改动的必要性：编码层级 + 案例属性。** 而且它不是理论推演，是你们自己的基准数据集里真实存在的结构。

## 五、设计方案

### 5.1 核心思路：一个底座，三种模式

不要把内容分析和主题分析做成两套功能。两者共享同一个底座：

```
        共享底座
   ┌──────────────────────┐
   │  编码树（可多层）      │  ← 主题分析要的"编码→主题"
   │  案例属性             │  ← 内容分析要的"类别×群体"
   │  可选多编码者 + 信度   │  ← 内容分析要的，主题分析可关
   │  备忘录（编码/主题级） │  ← 主题分析与扎根理论都要
   └──────────────────────┘
              │
      ┌───────┼───────┐
      ▼       ▼       ▼
   内容分析  主题分析  扎根理论
   （工作流模式切换呈现与默认值，不是切换代码路径）
```

**为什么这样设计：** 三种方法在"怎么编码"上确实不同，但在"编码之后怎么组织与检验"上共享同一批数据结构。做三套会三倍工作量且难以维护；做一个底座 + 模式切换，工作量约等于做一套。

### 5.2 数据模型改动（schema v1 → v2）

**编码对象（扩展）**
```python
{
  "id": "...",
  "name": "Experience with RDM",
  "definition": "...",
  "color": "#427d77",
  # ---- 新增 ----
  "parent_id": None,        # 父编码 id；None = 顶层（即"主题"）
  "kind": "theme",          # "theme" | "code"  —— 顶层为 theme，叶子为 code
  "memo": "",               # 编码级/主题级备忘录（TA 与 GT 必需）
  "anchor_examples": [],    # 锚例：该编码的典型引文（CA 的 coding agenda 必需）
  "inclusion": "",          # 纳入标准
  "exclusion": "",          # 排除标准
  "status": "final",        # "emergent" | "provisional" | "final"  —— TA 的主题演化
  "order": 0                # 同层排序
}
```

**文档对象（扩展）**
```python
{
  "id": "...", "name": "I1", "text": "...", "sha256": "...",
  # ---- 新增 ----
  "attributes": {},         # {"role": "R", "region": "华东", "satisfaction": 4}
  "created_at": "..."
}
```

**标注对象（扩展）**
```python
{ ..., "coder": "default" }   # 编码者标识，用于信度计算
```

**项目对象（扩展）**
```python
{
  ..., "schema_version": 2,
  "method": "thematic",        # "content" | "thematic" | "grounded" | "generic"
  "coders": ["default"],       # 项目内的编码者列表
  "attribute_keys": ["role"]   # 已登记的属性键（用于交叉表下拉框）
}
```

**迁移策略：** `validate_project` 已做 `schema_version` 校验。v1 → v2 迁移只需为已有对象补默认值（`parent_id=None`、`attributes={}`、`coder="default"`），完全向后兼容。已有的 377 条 TU Delft 标注不会受影响。

### 5.3 新增 API

```
# 编码管理（当前只有 add，缺 update/delete —— 这是必须先补的）
POST   /api/projects/{id}/codes/{code_id}          改名/改定义/改色/改父级/改 memo/锚例/状态
POST   /api/projects/{id}/codes/{code_id}/delete   删除（级联处理子编码与标注，写审计）
POST   /api/projects/{id}/codes/merge              合并两个编码（重指向标注）

# 文档管理（当前不能改名/删除/设属性）
POST   /api/projects/{id}/documents/{doc_id}          改名/设属性
POST   /api/projects/{id}/documents/{doc_id}/delete

# 分析（当前只有前端算的频次条形图）
GET    /api/projects/{id}/analysis/frequency       频次表：含计数、%、N、按层级汇总
GET    /api/projects/{id}/analysis/crosstab        交叉表：类别 × 属性
GET    /api/projects/{id}/analysis/reliability     信度：Cohen's κ / Krippendorff's α
GET    /api/projects/{id}/analysis/cooccurrence    共现矩阵（编码/主题两两共现）
```

**信度计算可以直接复用现有代码。** `evaluate.py` 里已经实现了 `iou()` 与**最大基数二分图匹配**（`match()` 递归函数）。编码者间信度需要的"配对 + 一致性统计"与它同构，只需把"引文 IoU 匹配"换成"同一片段被两位编码者赋予同一编码"的匹配，再套 κ / α 公式。**这是项目里最被低估的可复用资产。**

### 5.4 UI 设计

| 区域 | 现状 | 需要改成 |
| :--- | :--- | :--- |
| 左侧码表 | 扁平列表，仅能新建 | **缩进树**：折叠/展开、拖拽改父级、父节点显示子节点计数汇总、"未归组编码"高亮提示 |
| 编码详情 | 无（点侧栏只做筛选） | **编码详情面板**：定义 / 锚例 / 纳入标准 / 排除标准 / 备忘录 / 状态（涌现·暂定·定型）/ 改名 / 删除 / 合并 |
| 文档 | 只有名字 | 文档属性编辑器（键值对）+ 按属性筛选 |
| Insights | 频次条形图 + 矩阵 | 拆成四个标签页：**频次表**（含%）、**交叉表**、**信度**、**共现/主题地图** |
| 顶部 | 无方法选择 | **工作流模式选择器**（内容分析 / 主题分析 / 扎根理论 / 通用） |

### 5.5 工作流模式：直接回应你"按两种方法的流程设计"的想法

这是把方法论落进产品的地方。模式切换**不改变底层数据**，只改变默认值与界面重心：

**模式一：内容分析**
- 引导流程：先建**类别树** → 为每个类别填定义 + 锚例 + 纳入/排除规则（这就是 Mayring 的 coding agenda）
- 默认分析范围：**全部文本**（内容分析要求系统编码，不是选择性编码）
- AI 默认：**演绎模式**（只允许套用既定类别）
- Insights 默认页：**频次表 + 交叉表 + 信度**
- 显示信度面板：**开**

**模式二：主题分析**
- 引导流程：先**开放编码**（不要求预先建码表）→ 然后进"主题构建工作区"把编码拖进主题
- 侧栏持续提示：**"还有 N 个编码未归入主题"**（这是 TA 第 3–5 阶段的进度指示器）
- 备忘录：**突出**（编码级 + 主题级）
- AI 默认：**归纳模式**（允许提出新编码）
- Insights 默认页：**主题树 + 主题地图**
- 显示信度面板：**关**（反身性 TA 不要求信度）

**模式三：扎根理论**
- 编码带**阶段标记**：开放 / 主轴 / 选择性
- 持续比较：共现矩阵 + 备忘录并排
- 饱和追踪：显示"每新增 N 条标注出现新编码"的曲线，辅助判断理论饱和

**模式四：通用**（当前行为，给不关心方法标签的用户）

### 5.6 实施分期

| 阶段 | 内容 | 解锁 | 改动范围 |
| :--- | :--- | :--- | :--- |
| **P0** | 编码增删改（改名/定义/颜色）+ **`parent_id` 层级** + 编码级备忘录 + 码表树 UI | **主题分析** | `core.py` / `server.py` / `app.js` / `style.css`；schema v1→v2 |
| **P1** | 文档属性 + 属性编辑器 + 频次表（含%）+ **交叉表** | **内容分析**（统计侧） | 同上 |
| **P2** | 多编码者 + **信度面板**（复用 `evaluate.py` 的匹配算法）+ 共现矩阵 | **内容分析**（信度侧） | `evaluate.py` 扩展 + 新视图 |
| **P3** | 工作流模式切换 + 锚例/纳入排除规则字段 + 主题地图 | 方法学对齐 | 主要是前端 |
| **P4** | 扎根理论阶段标记 + 饱和追踪 | 扎根理论 | 中等 |

**建议从 P0 开始。** 它同时解锁主题分析、并为内容分析铺好路，而且是所有后续工作的前提（P1 的交叉表需要层级来汇总，P2 的信度需要编码可改名以避免歧义）。

## 六、回答你的判断

> "我觉得按照两种方法的操作流程设计就可以完成我们这个项目在 transcript coding 的任务了。"

**方向对，但需要修正一处关键认知：**

✅ **对的部分**：以方法流程为设计主线是正确的。QDA 工具的竞争力不在于"能编码"（这已经是标配），而在于**是否贴合某套方法学的工作流**。你们选择"同时服务内容分析与主题分析"是有差异化价值的——商业工具通常只优化一种。

⚠️ **需要修正的部分**：**编码这个动作本身，两种方法没有区别**——都是"选文本片段 → 贴标签"。所以"按两种方法设计"不会让编码任务变得"能完成"，它已经能完成了（缺的是我刚修的那个 UI bug）。

**真正的问题是"编码之后"**：
- 主题分析需要**把编码组织成主题**（层级）
- 内容分析需要**把编码变成可统计、可检验的类别**（属性 + 信度）

这两件事才是当前项目真正缺的，也正是你们的数据集（TU Delft 的 `[PM/SP]`/`[R]` 结构）已经暴露出的需求。

**所以我的建议是：** 不要分叉做两套功能，做**一个共享底座（编码树 + 案例属性 + 可选多编码者）**，再用"工作流模式"切换呈现重心。这样：
- 工作量约等于做一套，而不是两套；
- 底层数据模型只有一份，不会随方法增多而失控；
- 未来要加"框架分析（Framework Analysis）""模板分析（Template Analysis）"时，只需再加一个模式，不用动底层。
