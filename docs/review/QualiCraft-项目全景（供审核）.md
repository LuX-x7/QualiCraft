整理日期：2026-10-11

说明：本文是自包含的。审核者不需要访问代码库也能读懂；文末列出了**我自己已知的薄弱点**和**想请你判断的具体问题**。

## 一、一句话定位

> **一个本地优先的质性研究编码工作台。** 研究者自己编码，自己裁决 AI 的建议，最后导出可复现的期刊级图表和一份方法学记录。

三条不可让步的性质（写进了设计契约，冲突时以契约为准）：

1. **预览即脚本输出** —— 图只有一条渲染路径，导出的脚本就是画那张图的代码，不是另写一份"导出用的"。（输出是**可直接编辑的 SVG/PDF + 300dpi PNG**；不同期刊的格式要求不同，不宣称"期刊级"。）
2. **默认不出本地** —— 原文不参与任何网络调用；云端分析必须经人工确认。
3. **图上的每个数字都要能说清单位** —— 是编码行数，不是人数，不是重要性。

## 三、项目由三部分组成

```
qualicraft_eval/
├── qualicraft/          Python 标准库服务 + 分析引擎    3,123 行
│   ├── core.py          项目模型、编码本、标注、审计轨迹
│   ├── ingest.py        TXT / DOCX / OpenQDA CSV / NVivo CSV / ATLAS.ti XLSX / QualCoder .qda
│   ├── analyze.py       Project → tidy 表 + 四类派生统计量
│   ├── plotting.py      五类图 + 复现脚本生成
│   ├── ai.py            可选的 OpenAI 兼容端点调用
│   ├── datasets.py      五份公开语料的下载与 SHA-256 校验
│   └── server.py        HTTP 接口
├── web/                 工作台前端（原生 JS，无构建步骤）  1,833 行
└── website/             项目网站（Next.js + 自带 block CMS） 16,749 行
```

**为什么工作台前端没有框架**：核心工作流的目标是"零依赖、断网能跑"。
一个 1,800 行的 `app.js` 换来的是双击即用，不需要 node_modules。

> **口径要说准**：**核心的导入、编码、分析、导出全程只用 Python 标准库**；
> **只有绘图块需要 matplotlib**，缺依赖时该块停用、其余功能不受影响。见第九节第 5 条。

**为什么网站是 Next.js**：网站有内容编辑需求（block CMS），而且它是唯一需要构建的产物。

### 运行时分层

```
浏览器界面（英文，可切中文）
      │  loopback HTTP + 每进程令牌
Python 标准库服务
  ├── SQLite 项目存储
  └── 可选：OpenAI 兼容的模型端点（密钥只存在服务内存里，浏览器拿不到）
```

### 部署

`render.yaml` 定义两个服务，都是 free plan：

| 服务 | 运行时 | 启动 | 说明 |
|:--|:--|:--|:--|
| `qualicraft-workbench` | Python | `python run_demo.py` | 只读公开演示，绑 0.0.0.0，拒绝一切写入 |
| `qualicraft-website` | Node | `QUALICRAFT_PUBLIC_SITE=1 node start.js` | Next.js，`/w` 反向代理到工作台 |

两个服务的 `autoDeployTrigger` 都是 `off` —— 部署是**手动**的，这样一次提交不会悄悄把正在评审的版本换掉。

网站服务带 `healthCheckPath: /api/health`。**这是踩坑踩出来的**：默认探针打首页，而首页会初始化内嵌数据库（PGlite），在 0.1 核的免费实例上要 15–25 秒，探针等不到就判定服务已死 → 反复重启。

## 四、五大底座（产品骨架）

| # | 模块 | 输入 | 输出 |
|:--|:--|:--|:--|
| 01 | **Import** | TXT / DOCX / 其他工具的导出表 / 内置公开语料 | 文档 + 段落切分 |
| 02 | **Code** | 段落 + 编码本 | 标注（编码锚定到字符区间） |
| 03 | **Analyse** | 标注 | 频次 / 文档×编码矩阵 / 关系网 |
| 04 | **Plot** | 标注 | 图 + 计数 CSV + **画出这张图的脚本** |
| 05 | **Export** | 以上全部 | JSON / CSV / 矩阵 CSV / 方法学 Markdown |

**关键设计**：02–04 读的是**同一张 tidy 表**，不在阶段之间复制数据。所以第四步画的图和第三步的频率数**不可能对不上**——这是结构保证，不是纪律要求。

tidy 表列名固定：`case, code, parent_code, theme, start, end, text, source`。

## 五、核心设计决定（值得你挑战的地方）

### 5.1 三层结构：核心 / 可选块 / 真正不做

| 层 | 含义 | 谁决定 |
|:--|:--|:--|
| **核心** | 没有它就不是定性分析工具：文档、编码、标注 | 不可关 |
| **可选能力块** | 功能都在，默认不装，点一下就有 | 使用者决定 |
| **真正不做** | 方法论立场上不该做 | 极少，且写清理由 |

现有的可选块：主题归组、备忘录、AI 建议、频次分析、绘图工作台、审计轨迹。

**关掉一个块，它从界面上消失，而不是变灰。** 一个内容分析者和一个扎根理论者不该看同一个屏幕。
**用了哪些块会存进项目**，所以"这个研究用了哪些工具"本身是研究记录的一部分。

**真正不做的只有四条，而且每条都是立场不是成本**：

| 不做 | 理由 |
|:--|:--|
| 一键自动编码 | 定性研究的效度来自研究者的解释，不是模型的输出。AI 只提建议，必须人工裁决 |
| 云端账号体系 / SaaS | 数据不出本机是立足点，做成云端就是另一个产品 |
| 实时多人协作 | 同上 |
| 语义（向量）检索 | 研究者的检索需求是精确的，而向量检索**不可解释**——你不知道为什么这条被找到 |

### 5.2 AI 建议必须可溯源

每个建议锚定到字符偏移，**引文必须是原文里唯一可定位的精确子串，否则整条丢弃**。
建议不进入任何计数、图表或导出，直到人接受。接受/拒绝都写进审计轨迹。

### 5.3 共现有两种定义，都提供，且图注写明用的是哪种

| 口径 | 定义 |
|:--|:--|
| `overlap`（默认） | 同一访谈内，两条标注的**字符区间实际重叠** |
| `unit` | 两条标注落在**同一段落**内即算 |

两者数值不同。**"共现"这个词有多依赖定义，本身是要向读者交代的。**

### 5.4 计数单位必须写进图注（硬性要求）

- 频次/覆盖/共现的单位是**编码行**，不代表观点重要性，也不代表受访者比例
- 累计曲线按**文件名顺序**排列，不代表访谈时间顺序；**平台期不能证明**主题饱和
- 对角线数值是"该编码出现的单元数"，与其余格子口径不同

### 5.5 项目格式版本化，迁移幂等

`migrate()` 首次读取时原地升级，新增字段全是中性默认值，**编码本、标注和所有字符偏移原样保留**。
编码树每次写入都校验：不能自己是自己的父级、不能指向不存在的父级、不能移到自己后代下面。

## 六、公开数据与许可

工作台内置五份语料，覆盖四种**第三方工具的导出格式**：

| | 语料 | 规模 | 格式 | 许可 |
|:--|:--|:--|:--|:--|
| A | Open Science 访谈（Le Foll 2025） | 26 访谈 / 837 行 / 39 编码 | OpenQDA · CSV | **CC BY-SA 4.0**（有 ShareAlike） |
| B | 艺术与人文学科访谈（Bologna 2022） | 19 访谈 / 263 编码 | QualCoder · `.qda` | CC0 |
| C | 可复现研究产出（Loffreda & Chiarelli 2021） | 1008 行 | NVivo · CSV | CC BY 4.0 |
| D | 医疗从业者访谈（Wosny 2023） | 52 访谈 / 73 主题表 | ATLAS.ti · XLSX | CC BY 4.0 |
| E | FAIRqual 工作坊编码本 | ~50 行 | 编码本 · XLSX | CC BY 4.0 |

每份都做 SHA-256 校验，上游数据变了会**报错而不是静默产生不同结果**。每张图自动写入来源署名。

**注意口径**：A 和 C 都是 CSV（OpenQDA 与 NVivo 的列结构不同），D 和 E 都是 XLSX（一个是 ATLAS.ti 报表、
一个是纯编码本）。**TXT 和 DOCX 这两条导入路径没有语料覆盖**，只有单元测试。

**关于训练**：这些数据规模小、领域窄、编码体系各异，**不足以训练通用自动编码模型**。
可行路径是当作 few-shot 示例与评估集，且评估必须**按整份访谈留出**，不能随机切片（否则同一访谈的相邻段落会泄漏）。

## 七、真实数据验证（2026-10-11）

用两份真实的前列腺癌访谈（参与者 001/002，共 **50,086 字**）走完五大底座：

| 指标 | 值 |
|:--|:--|
| 编码本 | 36 个编码 / 7 个主题（全手工，未用云端 AI） |
| 标注 | 91 条 |
| 关系网 | 127 节点 / 128 连线（29 层级 + 91 编码 + **8 条共现**） |
| 图 | 7 张（SVG） |
| 导出 | 编码 CSV / 矩阵 CSV / 方法学 Markdown / 完整项目 JSON / 绘图脚本包 |

**验证中发现并修复的 bug**：按主题出图返回 500（`KeyError: 'code'`）——
绘图脚本里写死读 `r["code"]`，而按主题计数时 CSV 列名是 `theme`。
**这个 bug 在自带样例上完全测不出来，因为样例项目里没有主题。**

**一个方法论观察（不是验证结论）**：关系图的虚线连的是"同一访谈内区间重叠的编码"。
第一次跑完是 **0 条连线**——因为我把每条引文都编成了互不重叠的片段。
**我随后手工补了 7 条重叠编码**，才得到 8 条共现。所以这 8 条**不是编码结果的测量值，是我为了验证该视图而构造的输入**。
真正值得记的是这件事本身：**这张图会反过来引导编码行为**——它奖励重叠编码，一段一码的研究者永远看到空图。

## 九、我自己已知的薄弱点（请重点看这些）

1. **网站代码量严重失衡。** 一个三页的营销站用了 16,749 行 TS/CSS，而核心工作台只有 1,833 行。
   block CMS 是为"内容会频繁编辑"设计的，但这个站的内容其实很稳定。
   **这是我最怀疑的一处过度工程。**

2. **工作台前端是一个 1,800 行的单文件 `app.js`，没有构建步骤。**
   这是刻意的（零依赖），但已经很难维护：改一处样式要全文搜索，没有类型检查，没有组件边界。

3. **网站只有界面文案是双语的，区块内容是英文单语。** 中文页面上正文仍是英文。

4. **公开演示是只读的，且不能切换语料。** 访客只能看 Bologna 那一份，
   而五份语料的格式差异恰恰是产品的亮点之一。

5. **绘图块需要 matplotlib，这破坏了"零依赖"的前提。**
   设计文档里我建议过改用纯前端渲染，但那样就做不到"预览即脚本输出"。
   **这两个目标目前是冲突的，我选择了后者。**

6. **云端 AI 路径在本次会话中没有端到端跑通过**（没有 API key）。
   代码有测试，但真实调用未经我验证。

7. **审计轨迹按"连续同动作"合并。** 如果一天里操作是交错的（编码、改编码、再编码），
   仍会产生很多行。

8. **数据来源与许可只写进图的署名，没有更进一步的说明。**
   原先我写的是"衍生作品必须同样开放"——**这个法律判断过于确定，已删除**。
   实际该做的是：在方法学导出里写明数据来源、版本与许可，让读者自己判断。

9. **`render.yaml` 里的环境变量会被 Dashboard 覆盖，且不报错。**
   这导致过一轮"配置写对了但线上是旧值"的排查。目前只靠注释说明，没有校验。

## 十、想请你判断的具体问题

1. **网站和工作台的技术栈该不该统一？** 现在是 Next.js（网站）+ 原生 JS（工作台）+ Python（服务）。
   统一能减少认知负担，但工作台的"零依赖"前提会破。

2. **block CMS 该不该砍掉？** 换成普通的 MDX 或纯 JSX 页面，代码量可能降到 1/5。
   代价是失去"非技术用户可编辑内容"的能力——但目前的用户只有研究者本人。

3. **绘图块的依赖矛盾怎么解？** 选项：
   (a) 保留 matplotlib，接受"这个块需要装依赖"
   (b) 改纯前端渲染，放弃"预览即脚本输出"
   (c) 两者都做，让用户选（但就变成了两条渲染路径，正好违反设计原则）

4. **"真正不做"的四条，你同意吗？** 尤其"语义检索不可解释所以不做"——
   这是一个可以被挑战的判断。

5. **公开演示该不该开放更多？** 现在只读且只有一份语料。
   开放切换语料能让访客看到格式兼容性，但会引入写操作。

6. **还有什么明显该做而我完全没想到的？**

## 十三、针对第一轮审核意见所做的改动

外部审核（2026-10-11）给出了判断与一批新问题。以下是本轮的处理，供第二轮核对。

### 已核实：真实访谈数据不在仓库里

审核指出的第一优先级问题是伦理与数据。核查结果：

- 两份真实访谈稿**不在工作区、不在 git 历史（按特征词全文检索过所有提交）、未被 git 跟踪**

- `data/` 整体在 `.gitignore` 里，只有这一份公开演示库被显式放行

### 已改（代码）

| 项 | 改动 |
|:--|:--|
| **自动备份** | 每次改动后写一份可恢复 JSON 到 `data/backups/<项目 id>/`，保留 30 份；新增 `/api/projects/<id>/backups` 与 `restore-snapshot` 接口；顶栏显示快照数，失败时提示。**已补 5 个故障点测试**（见下） |

**备份的故障点测试**（`tests/test_backups.py`，共 85 个测试）：

1. 修剪永远不会删掉最新一份——**包括时钟回拨时**
2. 备份写不进去时，**编辑仍然成功**，且状态里会报告
3. 恢复一份快照**不动原项目**（这正是"原项目还在"的真实恢复场景）
4. 快照名无法逃出备份目录
5. 恶意 project id 无法逃出备份目录

**尚未验证的**：界面里完整走一遍（点快照 → 选一份 → 恢复为副本）。接口层已测，UI 层只做过手工检查。
