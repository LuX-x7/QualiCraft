# 我们没内置什么

> 标题借鉴 Pi Agent 的 "What we didn't build"。
>
> **但必须先把它的真实含义说清楚**——我最初理解错了，把「没内置」写成了「不做」。
>
> Pi 那份清单里的每一项，**都有明确的扩展路径**。原文写的是：
> - 没有内置 MCP 协议 → *"需要时通过扩展接入"*
> - 没有子代理 → *"或安装 `pi-sub-agent` 扩展"*
> - 没有计划模式 → *"新建一个 `TODO.md` 文件"*
>
> 而且 Pi 官方提供了 **50+ 扩展示例**（子代理、计划模式、权限门控、沙箱、MCP 集成……）。
>
> **所以 Pi 的立场是：不塞进核心，但一定给你路。** 这份文档按同样标准重写。

---

## 一、三层结构

| 层 | 含义 | 谁决定 |
| :--- | :--- | :--- |
| **核心** | 没有它就不是定性分析工具 | 不可关 |
| **可选能力块** | **功能都在，默认不装，点一下就有** | **使用者决定** |
| **真正不做** | 方法论立场上不该做 | 极少，且写清理由 |

---

## 二、核心（不可关闭）

| 核心 | 内容 |
| :--- | :--- |
| **文档** | 转录稿文本 + 字符坐标 |
| **编码** | 名称、颜色、在码表中的位置 |
| **标注** | 片段 → 编码 的对应关系 |

**为什么只有三样**：这三样构成了「定性分析」的最小定义。少任何一样，这个工具就不是定性分析工具了。

---

## 三、可选能力块（**都在，默认不装，点击添加**）

这是使用者「搭积木」的地方。**每一块都是真功能，不是占位符。**

| 块 | 提供什么 | 默认 |
| :--- | :--- | :---: |
| **主题归组** | 码表树、层级、父子关系、汇总计数 | 开 |
| **备忘录** | 文档级阅读笔记、编码级、主题级笔记 | 开 |
| **AI 建议** | 建议队列、采纳/拒绝、引文溯源 | 开 |
| **频次分析** | 编码频次、文档 × 编码矩阵 | 关 |
| **交叉表** | 类别 × 文档属性（内容分析必需） | 关 |
| **信度** | 多编码者、Kappa / Alpha | 关 |
| **绘图工作台** | **主题共现热力图、组别×主题发散条形图、混合研究气泡图**；配色/字号/聚类参数控件；SVG/PDF/TIFF 导出；复现代码导出 | 关 |
| **审计轨迹** | 完整活动记录、时间戳、可展开详情 | 开 |
| **REFI-QDA 导出** | `.qdpx` 导出，结果可导回 ATLAS.ti / NVivo | 关 |
| **音频转写** | Faster-Whisper 本地转写（需 GPU） | 关 |

### 关于绘图工作台（原 PRD 的「核心杀手锏」）

**它是可选块，不是被砍掉的功能。** 我上一版写错了，特此更正。

**它是可选的原因不是「不做」，而是**：

1. **它需要重依赖**（R / Docker / 绘图库），而本项目的立足点是「零依赖、断网能跑」。把它做成必装会破坏这个前提。
2. **不是每个研究都需要**。做访谈编码的人可能只要频次表；做混合方法的人需要气泡图。

**所以正确的做法是**：默认不装 → 需要出图的研究者点一下装上 → 装上后是全功能的，不是阉割版。

> 附带说明：原 PRD 计划用 Docker + R 沙箱。我仍建议**改用纯前端渲染**（Chart.js 等），只做那 3 张图但做到能投稿。理由是把 R/Docker 装进本地部署会把门槛从「双击运行」抬到「先装 Docker」——这与「大道至简」冲突。这是实现方式的分歧，不是「做不做」的分歧。

### 怎么添加

侧栏底部「工具」入口 → 列出全部能力块 → 点击开关即装即卸。

- **状态存进项目**，所以「这个研究用了哪些工具」本身是研究记录的一部分
- 关掉 = 界面上完全消失（不是变灰）
- 每个块可以独立开关，也可以按工作流模式预设

## 四、真正不做（很短，且都有方法论理由）

这一层才是「不做」。判断标准是：**它违背本项目的立场，而不只是成本高。**

| 不做 | 理由 |
| :--- | :--- |
| **自动编码**（一键生成全部编码） | **方法论立场**。定性研究的效度来自研究者的解释，不是模型的输出。AI 只提建议，必须人工裁决。这不是能力问题，是立场问题。 |
| **云端账号体系 / SaaS** | 数据不出本机是本项目的立足点。做成云端就变成了另一个产品。 |
| **实时多人协作** | 同上。多人意味着服务器、账号、加密、审计——那是另一个产品。 |
| **语义（向量）检索** | **产品边界**。本工具的检索需求是精确的——"所有提到数据共享的引文"，要的是可枚举、可复核的结果。语义检索改变的是这个产品是什么，不是它做得好不好。附带一点：向量检索的召回理由难以向读者交代，而关键词命中可以直接指出。 |

**注意这一层只有 4 条，而且每条都是「立场」不是「成本」。** 上一版我把「多媒体编码」「通用绘图引擎」「词云」都塞进这里，那是错的——它们只是成本高或场景窄，应该放可选块。

## 六、范围决定（是决定，不是缺陷的默认接受）

这一节与「真正不做」不同：这些功能**没有人从方法论上反对**，只是**当前不在范围内**。
写在这里是为了让它们**被看见**，而不是让下次审核把它们当成遗漏。

| 决定 | 理由 | 如果要做 |
| :--- | :--- | :--- |
| **快照（Snapshots）对话框只在宽屏提供** | 它做的是**从备份恢复项目**——一个针对研究项目的恢复动作，而项目本身在电脑上。在手机上恢复一个不在手机上的项目，不是使用场景。窗口宽度 ≤800px 时，入口按钮（`.save-state`）由样式表隐藏。 | 放进 `projects` 菜单，或加一个溢出菜单。需要新的测量与截图。 |
| 手动编码对话框在 390px 可用 | 已实测：Import / Create code / Export 三个对话框在 390px 下均为 356px 宽、不溢出、关闭按钮在视口内。 | —— |

## 五、这份清单怎么用

1. **想加功能时先看这里。** 如果在「可选块」里，做成块就行；如果在「真正不做」里，需要先讨论是否要改立场。
2. **汇报时用它。** 导师问「为什么不做 X」，分三种回答：
   - 在核心？→ 已经有了
   - 在可选块？→ **有，默认没装，需要可以点开**（这是最好的回答）
   - 在真正不做？→ 讲立场
3. **它是活的。** 决定被推翻时**不要偷偷删掉**，改成「曾考虑过，因为 X 放弃，后来因为 Y 重新评估」——那本身就是一份设计记录。
